# Аналитика: формулы, источники и ограничения

Обновлено 26 октября 2026. Контракт: `GET /api/v1/admin/analytics/report`.
Старый `/admin/analytics/dashboard` сохранён совместимым и использует свою прежнюю UTC-методику.

## Период и денежная база

Обязательные `start_date`, `end_date`: ISO-даты, от 1 до 366 дней включительно,
в пределах 1900–2200 годов. `timezone`: Asia/Dushanbe (по умолчанию), Asia/Tashkent
или UTC. Первые два пояса имеют фиксированный UTC+05. SQL получает UTC-границы
полуоткрытого интервала `[полночь start_date; полночь end_date + 1 день)`.

Все денежные показатели отчёта используют **только заказы в TJS**. Суммирование
разных валют запрещено; валютной конвертации нет. Числа в API — Decimal, в JSON — строки.

Действующий заказ: текущий `orders.status` не `cancelled` и не `returned`.
Стоимость заказа — `orders.total`: после скидок и списанных бонусов, с доставкой.
Это забронированная стоимость, **не выручка по подтверждённым поступлениям**.
Подтверждение, доставка и завершение заказа не доказывают факт оплаты.

При `category_id` отчёт выбирает целые заказы, содержащие товар непосредственно
из этой категории (без автоматического включения дочерних категорий). Итоги,
единицы и разбивки учитывают **все позиции этих заказов**, в том числе других
категорий. Это анализ когорты заказов с выбранной категорией, а не распределение
доставки и скидок на отдельные товары. Такая область указана в интерфейсе.

## Формулы

| Поле | Формула | Источник |
| --- | --- | --- |
| order_value | SUM(total) действующих заказов периода | orders |
| orders | COUNT(id) всех заказов периода, включая отмены/возвраты | orders |
| valid_orders | COUNT(id) действующих заказов периода | orders |
| average_order_value | order_value / valid_orders, округление до 0,01; 0 при пустой базе | orders |
| buyers | COUNT(DISTINCT user_id) действующих заказов периода | orders |
| repeat_buyers | Покупатели периода, у которых есть действующий TJS-заказ раньше начала периода | orders; история всех категорий |
| Покупатели с первым заказом | buyers − repeat_buyers | orders |
| Заказов на покупателя | valid_orders / buyers; нет значения при buyers=0 | orders |
| Стоимость на покупателя | order_value / buyers; нет значения при buyers=0 | orders |
| units | SUM(quantity) позиций действующих заказов | order_items + orders |
| discounts | SUM(discount + points_discount) действующих заказов | orders |
| shipping | SUM(shipping_cost) действующих заказов | orders |
| cancelled | COUNT текущего статуса cancelled в когорте | orders |
| returned | COUNT текущего статуса returned в когорте | orders |
| returned_order_value | SUM(total) текущих returned заказов когорты | orders |
| categories / brands | SUM(quantity), SUM(line_total) по текущей категории/бренду товара | order_items + orders + products + categories/brands |
| products | До 50 товаров по SUM(quantity), затем id; стоимость SUM(line_total) | order_items + orders + products |
| stocks | Количество SKU с остатком >5, 1–5, ≤0; SUM положительных остатков | products.stock_quantity |
| products_without_sales | SKU без позиций в действующих заказах выбранного периода | products + order_items + orders |
| low_stock_products | До 50 SKU с остатком ≤5, по остатку, затем id | products |
| procurement_signals | SKU с остатком ≤5 или продажами со склада за 30 дней; темп = списания / 30; запас дней = текущий остаток / темп | products + stock_movements |
| slow_movers | До 50 активных SKU с остатком >5 без списаний за 30 дней | products + stock_movements |
| stale_orders | До 20 активных заказов без обновления 48 часов, по давности обновления | orders.updated_at |
| cancellation_reasons / return_reasons | Частоты причин из `Причина:` в заметке перехода; старые записи без причины выделены отдельно | order_status_history.note |
| demo_orders_in_period | Заказы с маркером `[DEMO ANALYTICS]` в выбранном периоде, включая отмены и возвраты | orders.customer_note |
| demo_gross_profit | Только demo-заказы: 28% суммы товарных позиций действующих заказов; без доставки, скидок и операционных расходов | demo order_items |
| statuses | COUNT заказов каждого текущего статуса | orders |
| reached_stages | COUNT(DISTINCT order_id) по to_status, для заказов выбранной когорты | order_status_history + orders |
| processing_hours | AVG(первая дата перехода − created_at заказа), в часах, по этапу | order_status_history + orders |

Стоимость позиций в разрезах — **до скидок на заказ и без доставки**. Поэтому сумма
категорий/брендов не обязана совпадать с order_value. В модели нет исторических
снимков категорий и брендов: перенос товара меняет его аналитическую принадлежность.
Переименование товара в таблице лидеров тоже использует текущее название.

Demo gross profit — намеренно учебная цифра с условной себестоимостью 72% от цены.
Она отображается только при наличии временных demo-заказов и не является реальной
прибылью или бухгалтерским показателем. Удаление demo-набора выполняется командой
`python -m app.demo_analytics clear`.

Остатки всегда текущие, с учётом черновиков и архива каталога, а не на историческую
дату. Фильтр категории для склада ограничивает непосредственно товары категории.
Нулевые продажи не равны низкому спросу: просмотры и время наличия не анализируются.

Возвраты относятся к **дате создания заказа**, а не дате возврата. Возвращённая
стоимость не доказывает, что деньги уже перечислены клиенту. Частичных возвратов
в текущей модели нет. Изменение текущего статуса может изменить прошлый отчёт.

Причины отмены и возврата вводятся сотрудником обязательным списком для новых
переходов и сохраняются в заметке истории с префиксом `Причина:`. Старые записи
могут не иметь причины; свободный текст автоматически не классифицируется.
Сигнал «без обновления 48+ часов» использует `orders.updated_at` для активных
заказов и показывает давность последнего изменения, а не длительность этапа.

Запас в днях — ориентир по списаниям со склада за 30 дней, а не прогноз точки заказа.
Сроки поставки поставщиков не хранятся; сезонность и короткий период не учитываются.

Путь заказа — реальные записанные этапы за всё время жизни выбранной когорты.
Повторный вход в этап учитывается один раз. Пропущенные этапы не выводятся из
финального статуса. Время измеряется от создания до первого входа, а не между
соседними этапами; отрицательные интервалы исключаются. При отсутствии истории
этап имеет 0 наблюдений и недоступное время. Не предполагается монотонная воронка.

## График, сравнение и экспорт

По умолчанию предыдущий период непосредственно предшествует текущему и имеет ту же
длину. При `comparison=previous_year` сравниваются те же календарные даты год назад;
29 февраля сопоставляется с 28 февраля невисокосного года.
Изменение = `(current − previous) / previous × 100%`. При previous=0 процент
не вычисляется: интерфейс показывает отсутствие базы сравнения.

SQL группирует календарные дни в выбранном поясе. Пропущенные даты дополняются
нулями. `grain=day|week|month`: недели с понедельника, месяцы с первого числа.
Крайние группы могут быть неполными. Для `previous_period` сравнение совмещено по
смещению в днях и не является сравнением одноимённых календарных дат.
Подпись группы — начало календарной недели/месяца, иногда раньше start_date.
Сумма точек каждого периода равна его order_value; счётчик orders включает отмены.

CSV экспортирует сводку обоих периодов, динамику, лидеров продаж, сигналы склада,
застоявшиеся заказы и причины отмен/возвратов. UTF-8 с BOM,
денежная единица TJS указана в заголовках. Категорийная область та же, что на экране.
CSV не содержит персональных данных покупателей. Таблица графика доступна в details.

## Что намеренно недоступно

- Реальная оплаченная выручка: нет реестра подтверждённых платежей.
- Прибыль, маржинальность, стоимость запасов: нет достоверной себестоимости/расходов.
- Маркетинговая конверсия и каналы: нет полной модели событий и атрибуции.
- LTV: полная история поступлений/затрат не реализована; средняя стоимость заказов
  покупателя не называется LTV.
- Когортное удержание и RFM: пока не реализованы.
- Оборачиваемость: нет среднего исторического остатка/себестоимости.

## Безопасность и производительность

API защищён `VIEW_STATISTICS` на сервере. Покупатели получают 403, гости 401.
Некорректные даты/масштабы/пояса отклоняются до агрегации. ORM-коллекции заказов
не загружаются: SQL-агрегаты, EXISTS и подзапросы исключают N+1. Интервал ограничен
366 днями; график читает максимум 732 агрегированных дневных строки, разрезы по
50 строк. Складские итоги вычисляются одной строкой условных SUM.
Используются существующие индексы created_at, order_id, product/category/brand.
Тест ограничивает количество SQL-запросов отчёта (≤25 для годового периода).

Серверного кэша нет: нет проблемы его инвалидации при смене статусов/остатков.
Frontend использует текущую настройку TanStack Query staleTime=30 секунд и кнопку
обновления. Для больших production-баз нужны EXPLAIN и измерения на реальном
объёме, затем индексы/материализация по результатам. PostgreSQL-ветвь подготовлена,
но в этой сессии проверена только SQLite.
